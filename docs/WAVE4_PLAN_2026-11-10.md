## A. ZKTeco: old punches missing, queue flooding, startup freeze

### What is actually happening (confirmed in code)

**1. Punches from PINs that aren't registered yet are thrown away.**
- When a device sends a punch for a PIN with no employee assigned, the app shows it in the live log and **stops** (`zkteco_network_service.dart:581-587`). Nothing is saved.
- The "save unmapped punch" call was removed in commit `fedab7b` (Sep 2026). So `processPendingUnmappedPunches` has nothing to replay once the PIN is assigned.
- The punch's duplicate-check key is recorded **before** this point (`:491`). The same punch is then ignored for 24 h, and after that the device poll no longer reads it (see 2).
- **Result:** every punch from before an employee's PIN was set up, or from a mistyped PIN, is lost.

**2. The device poll only re-reads one day back.**
- Each poll keeps only records newer than "last poll − 1 day" (`:1926-1935`).
- The "last poll" mark is saved before the punches are actually processed (`:2075`, `:2124`). If the app closes mid-way, those punches are skipped for good.
- Other time limits:
  - ADMS push drops punches older than 3 days (`:425`).
  - The cloud replay only looks back to its last run (`:1672`).

**3. Why it flooded the queue before, and still can.** Three sweeps re-queue every attendance record that doesn't look "synced":
- `syncAllRecordedAttendanceToFirestore` (`:1947`). It runs at start, on every Attendance-tab open, from Employee Management and from the server. It uses `forceUpload`, which skips the guards.
- `SyncService._enqueueMissingAttendance` (`sync_service.dart:1374`).
- The server sweep (`server.dart:8161`). It runs at server start and on every desk catch-up (5-min cooldown).

The "looks synced" test fails for records that are already in the cloud, so they are re-sent:
- Records downloaded from the cloud get `syncStatus: synced` but not `synced: true` (`local_storage_service.dart:2582`, `finance_local_storage.dart:4423`).
- Downloads also create extra alias copies (`{pin}_{date}`), which are never marked synced (`finance_local_storage.dart:4432`).
- The server marks records synced without clearing `pendingSync` (`server.dart:9369`).
- A once-per-session "heal" step flips synced records with no `lastSyncedAt` back to pending (`sync_service.dart:738-758`).

**4. Startup freeze (~60 s).**
- `startServer()` runs at launch (`main.dart:321`) and replays up to **2,000 cloud punches** (7 days) when the last replay is over an hour old (`zkteco_network_service.dart:1618`).
- It handles them one by one on the screen thread, with no pause between them and a full debug print each.
- The box-opening order in the clinic perf log (credentials → employees → attendance → 60 s gap) matches this path exactly.

**5. Smaller risks (need confirmation):**
- A punch added to the same employee-day while that day is uploading can be marked "synced" without being sent (`sync_service.dart:3940-3958`).
- The cloud upload replaces the whole `punches[]` list, so two PCs writing the same employee-day overwrite each other.

### The fix, in this order (flood-proofing first, then recovery)

| Step | Change | Why this order |
|---|---|---|
| **A1** | **One reliable "already uploaded" test** used by all three sweeps: `syncStatus == 'synced'` and `pendingSync != true`, or `synced == true`. Downloads mark records properly synced (`synced`, `pendingSync: false`, `lastSyncedAt`). Alias copies are never queued. The server clears `pendingSync`. The heal step only touches records that hold punches and were never uploaded. | Stops the re-queue loop **before** anything new is recovered. Without it, step A3 would re-trigger the old flood. |
| **A2** | **Sweeps stop bypassing the guards.** No `forceUpload` on sweeps. Old days carry the `backlog` flag, which uses the daily backlog share and is skipped if already queued. No sweep on every Attendance-tab open. The server sweep runs at most every 30 min, not on every desk catch-up. | Turns sweeps into a safety net instead of a hammer. |
| **A3** | **Unregistered-PIN punches are saved again**, in `local_unmapped_punches`, under a fixed key `device_pin_yyyyMMddHHmmss` (saving twice changes nothing). The duplicate-check key is recorded only **after** a punch is saved or routed, so a failure no longer hides the punch for 24 h. When a PIN gets assigned, its saved punches are replayed and each is deleted only after it is recorded. | Stops new punches being lost. |
| **A4** | **One-time catch-up of missed punches from the devices.** Once per device: ignore the "last poll" mark one time and re-read punches back to a fixed date (**D1**). Process in chunks of 200 with pauses between chunks, saving progress after each chunk so it can resume. Runs from the 5-minute poll timer, **never at startup**, and only on the poller PC (the LAN server). Re-reading is safe because a day record ignores a punch it already holds (`:776-780`), and each employee-day becomes one queue item, merged. | Recovers the old punches exactly once. |
| **A5** | **The "last poll" mark is saved only after its punches are processed.** | Closes the "app closed mid-way" gap for the future. |
| **A6** | **Mark "synced" only if the record is unchanged** since it was sent (same punch count / last punch time); otherwise it stays queued. | No punch marked uploaded without being sent. |
| **A7** | **Startup freeze:** the cloud punch replay starts 2 min after launch, works in chunks with pauses, and drops the per-punch full debug print. Timing marks are added so the next perf log confirms it. | The likely ~60 s startup freeze. |
| **A8** (**D3**) | **Cloud upload merges punches instead of replacing the list** (`arrayUnion` of punch entries, then check-in/out recalculated), so two PCs don't overwrite each other. | Only if D3 = yes. It changes how the cloud record is written. |

**Safety net for the rollout:**
- A one-line count in `gmwf_sync.log` after each catch-up chunk: punches read, recorded, already present, queued.
- A cap of at most N new attendance queue items per pass.

If the numbers look wrong, delete the `zk_backfill_v1` flag (or set it as done) to stop the catch-up.

## B. Stock: remaining double-counting edges

| Item | Change | Risk |
|---|---|---|
| **B1: Desk loses LAN but has internet → dispense counted twice in the cloud (4.6, confirmed)** | The desk gives each dispensed line a fixed ID, `disp_{branch}_{serial}_{entry}_{medicine}`. It uses that ID in its own queue and sends it in `deductedBatches`; the server copies it into its queue item (`server.dart:7397`). The cloud's once-only marker then catches the second copy. | Low. A legitimate second dispense of the same token + medicine (re-dispense after reversal) needs a different ID, so the ID includes the dispense time. |
| **B2: Editing a medicine's name/dose/expiry creates a new record (4.7, confirmed)** (`request.dart:3262-3284`) | **D4.** (a) Edit in place: the ID stays, only fields change. (b) Keep new IDs, but the old record keeps `mergedInto: newId` and stock uploads for the old ID are redirected. | (a) is simpler, but other code may look medicines up by the generated ID; this will be checked before changing. |
| **B3: Version box opened with two types (2.8, confirmed)** (`realtime_router.dart:57` opens `Box<int>`, but the same file reads it untyped at `:197`/`:263`) | Open it untyped. | **D5.** This switches on the stale-message check that has silently been failing (129 errors). It is the intended behaviour, but has never actually run at the clinic. |
| **B4: Medicine restrictions re-downloaded on every LAN event while the server link is down (2.9)** | Same cooldown and in-flight guard as `downloadTodayTokens`. | Low. Restrictions may be up to the cooldown old. |

## C. Smaller leftovers (low risk, one commit)

- **Syringe/needle auto-deduction can share a queue key** with a prescribed syringe of the same ID (`patient_form.dart` `_deductSyringeIfNeeded`). Combine them into the per-medicine total, as Wave 1 did for medicines.
- **Two upload passes at once** on the LAN server (`server_sync_manager.dart:1469`). Set the busy flag before the first wait.
- **Home quick-actions scan the whole food-token box on every redraw** (`home_snapshot_widgets.dart:2650`). Cache the count.
- **Kitchen screen branch guard.** Keep the original branch at load, so the same "never fall back to Karachi" check as the Office Boy screen can apply.
- **Reversing another PC's not-yet-uploaded tokens** can make them reappear in the cloud. Send the reversal over LAN to the issuing PC, which then takes them out of its own queue.
- **Doctor PCs may apply restock changes twice** (`doctor_right_panel.dart:251-262`; needs confirmation). Use the same once-only check the router uses.

## Decisions needed

- **D1: How far back should the punch catch-up go?**
  - (a) Since 12 Sep 2026, when unmapped punches stopped being saved. **Recommended.**
  - (b) 90 days.
  - (c) 30 days.

  Devices only hold what their memory keeps; older punches may already be gone from the device.
